## 3.10 Ingestion routing

### 3.10.1 What the router is

A pure classifier that sits between the messaging adapter and Stage 1. It takes
bytes that have already been downloaded and decides what they are. It does not
call a model, does not touch the database, and does not write files.

```
Telegram adapter  ->  router.classify()  ->  RoutedInput  ->  Stage 1 extraction
```

It is testable with no API key, no bot token and no network, which is why it sits
at commit 5 in section 17.

### 3.10.2 What arrives

Telegram can deliver a receipt in five shapes, and the bot must accept all of
them without ever asking the user to change how they send one (invariant 10):

| Shape | How it arrives | Notes |
|---|---|---|
| Compressed photo | `message.photo`, largest size | Telegram re-encodes to JPEG and caps the long edge. The default when you tap the camera icon. |
| Uncompressed image | `message.document`, image MIME | What "send as file" produces. Higher fidelity, same content. |
| PDF | `message.document`, `application/pdf` | Assumed to be a scan or an exported image, per the decision above. |
| Plain text | `message.text` | `/add 400 chai`, or free text. Section 3.9. |
| Anything else | video, sticker, voice, location, contact | Not a receipt. |

### 3.10.3 The routing rules

**R1. Everything that is not text becomes one or more images.** There is exactly
one extraction path in v0. A PDF is rasterized page by page with `pypdfium2` and
each page is handed on as an image. No text-layer detection, no branch, no
ambiguity to resolve.

**R2. When a message carries both a photo and a document, prefer the document.**
It is the uncompressed original. The compressed copy is discarded without
comment. The user is never told they sent it the better way or the worse way.

**R3. The dedupe hash is taken from the bytes as received, before anything
else happens.** SHA-256 of the original file. For a PDF, that is the PDF bytes,
not the rendered pages, so re-rendering later cannot change the identity of the
receipt. This is the primary dedupe key from section 3.6 as revised by 24.4.

**R4. A multi-page PDF is one receipt, not several.** All pages up to a cap are
rasterized and passed to a single extraction call as multiple images. The cap
exists so a mistakenly forwarded 200-page statement cannot spend the daily budget
in one message.

**R5. Each photo in an album is its own receipt.** Telegram delivers a media
group as separate messages sharing a `media_group_id`. Three photos sent together
become three receipts with three confirms. Stitching several photos into one
receipt is deliberately not attempted in v0.

**R6. Text goes to the text path, not to vision.** Classified as `TEXT` and
handed to the small text-parse call in section 3.9. No image, no reconciliation
gate, `reconciled` is null rather than false.

**R7. Anything else is `UNSUPPORTED`, with a reason.** The bot says what it can
read. It does not tell the user to resend, recrop, retake or reformat.

**R8. Detection is never ambiguous.** Every input lands in exactly one of
`IMAGE`, `TEXT`, `UNSUPPORTED`. There is no "probably" branch and no confidence
score, because there is only one extraction path to route to.

### 3.10.4 What the router must never do

This list is the reason the router is a separate module rather than a few lines
inside the Telegram handler.

- **No image editing, rotation, cropping, deskewing, denoising, upscaling,
  contrast adjustment or enhancement of any kind.** Invariant 9. Section 7.2
  explains why: generative or filter-based editing repaints pixels, and
  repainting pixels near an amount is silent corruption on a financial ledger.
- **No re-compression.** Bytes are passed through as received.
- **No model calls.** Routing is deterministic.
- **No storage.** It returns a value, it does not persist one.
- **No instructions to the user about how to send a receipt.** Invariant 10.

### 3.10.5 The boundary that invariant 9 does not cover

Rasterizing a PDF page produces pixels that did not previously exist as pixels,
and decoding HEIC to JPEG produces different bytes for the same picture. Neither
is editing, upscaling or enhancement, because neither changes what the image
depicts. Both are format decoding.

**Proposed rule: decoding and rendering are permitted, altering is not.** A
transform is permitted only if it is deterministic, lossless with respect to
content, and would produce a visually identical result on every run. Rasterizing
at a fixed DPI and transcoding a container both qualify. Sharpening,
straightening and upscaling do not.

### 3.10.6 The output

```
RoutedInput
    kind                 IMAGE | TEXT | UNSUPPORTED
    images               list of (bytes, mime_type)   empty unless IMAGE
    text                 str | None                   set only when TEXT
    source               telegram_image | telegram_pdf | telegram_text
    original_sha256      str | None                   the dedupe key, R3
    page_count           int                          1 for a photo
    rejection_reason     str | None                   set only when UNSUPPORTED
```

`source` maps one to one onto `raseed.db.models.Source`, which already exists.

### 3.10.7 Numbers that need to be set

These are the only tunable values in the router. Proposed defaults:

| Constant | Proposed | Reasoning |
|---|---|---|
| `MAX_PDF_PAGES` | 5 | A receipt is one page. Five absorbs a cover page or a duplicate without letting a forwarded statement run away. Beyond the cap the router rejects rather than truncating silently. |
| `PDF_RENDER_SCALE` | 2.0 | Roughly 144 DPI. The eval set was rendered at `device_scale_factor=2` and reads cleanly, so this matches known-good input. |
| `MAX_FILE_BYTES` | 20 MB | The Telegram Bot API download ceiling. Anything larger cannot be fetched, so rejecting earlier is honest. |
| `ACCEPTED_IMAGE_MIME` | jpeg, png, webp, heic, heif | What phones actually send. |

### 3.10.8 What was deliberately dropped, and what it costs

The PDF text-layer path is not built. A quick-commerce invoice with selectable
text could have been parsed by `pdfplumber` for free and with perfect accuracy,
skipping the vision call entirely. Instead every PDF costs tokens and inherits
the vision model's error modes.

That is an accepted cost, on the grounds that a scanned or exported-as-image PDF
gets no benefit from the branch and Ashrit expects most PDFs to be exactly that.

**Reopen this if** PDFs turn out to be common *and* their text selects. The check
is thirty seconds: open one and try to highlight a line. `pdfplumber` stays on the
allowlist so the branch can be added without a dependency conversation.

## Open questions for Ashrit

These change the text above, so they are worth answering before this is merged
into the brief.

1. **Should PDFs be rasterized, or refused outright in v0?** The draft rasterizes
   them, because refusing would mean telling the user to send it differently,
   which invariant 10 forbids. Refusing is a one-line change if you prefer it.
2. **Is 3.10.5 the right line on invariant 9?** Rasterizing and transcoding are
   not editing under the proposed rule, but invariant 9 is written absolutely and
   this is the first place it needs a boundary. This is the question in this
   document most worth your attention.
3. **Is "I can read receipt photos and PDFs" an instruction under invariant 10?**
   The draft treats a capability statement as permitted and a request to resend as
   forbidden. Confirm.
4. **One receipt per photo in an album (R5), or should tall receipts split across
   photos be stitched?** The draft does not stitch. Note that a single very tall
   image is a different problem, and it belongs to the missing section 3.11.
5. **Is `MAX_PDF_PAGES = 5` right,** or should a multi-page PDF be refused
   entirely?
